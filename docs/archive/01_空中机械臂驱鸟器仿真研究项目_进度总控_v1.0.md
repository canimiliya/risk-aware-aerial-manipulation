## 0. 文件权威性与使用规则

1. 本文件负责记录项目当前进度，不替代权威总纲中的研究目标、技术边界和实验要求。
2. 权威层级固定为：

```text
项目负责人最新明确决策
        ↓
00_权威总纲
        ↓
01_进度总控与协作协议
        ↓
已批准的阶段任务卡
        ↓
执行 Agent 的实现与报告
```

3. 项目负责人拥有最高决策权。高级总控 AI、低级执行 Agent 和 GitHub 中的任何历史记录均不得覆盖项目负责人的最新明确决定。
4. GitHub 仓库是代码、配置、文档、任务证据和审查记录的统一事实来源。聊天中的结论只有在与仓库提交对应后，才视为正式项目证据。
5. 每轮低级执行 Agent 完成任务后，必须提交 GitHub，并在聊天中返回执行报告、分支、完整 commit、测试结果和已知限制。
6. 高级总控 AI 必须优先读取 GitHub 中的真实修改、提交差异、日志和状态文件，再判断任务是否通过。不得只根据低级 Agent 的文字报告直接批准。
7. 上一任务未经高级总控 AI 审查、项目负责人确认前，不得自动开始下一项重大任务。
8. 本文件只记录已经发生或已经批准的事实。未知内容必须标记为 `UNKNOWN`、`WAITING_INPUT` 或 `NOT_VERIFIED`，不得猜测。

# 第一部分：项目协作架构

## 1. 角色与权限

### 1.1 项目负责人

**角色：** 用户。  
**权限：** 项目最高决策者。

主要职责：

- 决定研究方向、技术路线和资源投入；
- 决定任务是否继续、暂停、返工或转向；
- 审阅高级总控 AI 的诊断结论；
- 提供 GitHub 仓库、本地工作区和硬件信息；
- 批准重大依赖安装、长训练、平台切换和研究范围变更。

### 1.2 高级总控 AI

**建议模型：** 高推理强度的 GPT-5.6 系列。  
**角色：** 研究总控、技术审查者和任务设计者。

主要职责：

- 维护权威总纲和进度总控；
- 通过 GitHub 检查低级 Agent 的真实提交；
- 审查代码差异、测试、日志、配置和实验数据；
- 判断任务状态：通过、有限通过、返工或阻断；
- 用项目负责人能够理解的语言解释审查结果；
- 在项目负责人确认后，生成下一张唯一任务卡；
- 防止低级 Agent 擅自扩展范围、伪造结果或绕过阶段门槛。

高级总控 AI 原则上不直接代替低级 Agent 完成大规模工程实现；必要时可以修订文档、任务卡、审查脚本和少量关键补丁。

### 1.3 低级执行 Agent

**建议模型：** GPT-5.6 Luna / Codex 执行环境。  
**角色：** 实际编码、安装、运行、测试和证据收集者。

主要职责：

- 严格按照唯一任务卡执行；
- 直接修改本地项目；
- 运行要求的命令、测试和实验；
- 保存原始日志和失败证据；
- 提交 GitHub；
- 在聊天中返回结构化执行报告；
- 不得自行修改研究方向、扩大任务边界或跳过门槛。

### 1.4 辅助解释工具

遇到专业术语、公式、代码或论文内容难以理解时，可以使用：

1. 截图后交给豆包进行初学者解释；
2. 在 ChatGPT 网页版创建聊天分支进行专项解释；
3. 单独开启学习对话，避免污染项目总控上下文。

辅助解释工具只负责帮助理解，不具备项目批准权，其结论不能直接替代 GitHub 证据和高级总控审查。

        ↓

        ↓

        ↓

        ↓

### 禁止的错误流程

```text
低级 Agent 自称完成
→ 高级总控不查 GitHub 直接相信
→ 自动生成下一任务
```

```text
上一任务失败
→ 不定位原因
→ 直接增加训练时长或切换算法
```

```text
多个低级 Agent 同时修改同一主线
→ 没有分支隔离和提交边界
→ 无法判断结果来源
```

## 5. 提交规则

推荐提交格式：

```text
<type>(<scope>): <summary>
```

常用类型：

- `chore`：环境、目录、依赖和工程维护；
- `feat`：新功能；
- `fix`：错误修复；
- `test`：测试；
- `docs`：文档；
- `refactor`：不改变外部行为的重构；
- `exp`：实验配置和结果；
- `repro`：第三方论文或官方示例复现。

示例：

```text
chore(s0): initialize project workspace
repro(s1): reproduce official AM-Planner grasp task
fix(s3): correct quaternion convention in trajectory bridge
```

每个任务最终必须提供完整 40 位 commit SHA，不得只提供模糊截图或口头说明。

## 6. GitHub 审查最低证据

高级总控 AI 审查每轮任务时，至少应检查：

1. 当前分支和基准 commit；
2. 最终 commit；
3. `git diff` 或 Pull Request 文件差异；
4. 新增、修改和删除文件；
5. 测试命令及退出码；
6. 原始日志和配置；
7. 是否修改任务范围之外的文件；
8. 是否存在未提交修改；
9. 是否存在大型二进制文件、密钥或个人隐私；
10. 低级 Agent 的报告是否与仓库事实一致。

正式实验还必须检查：随机种子、完整配置、checkpoint 哈希、原始 episode 结果和绘图脚本。

## 7. 统一状态

所有阶段、任务和门槛只使用以下状态：

| 状态 | 含义 |
|---|---|
| `NOT_STARTED` | 尚未开始 |
| `WAITING_INPUT` | 等待项目负责人提供必要信息 |
| `AUTHORIZED` | 已获准开始，但尚未执行 |

| `CANCELLED` | 经项目负责人决定取消 |
| `SUPERSEDED` | 已被新版本或新决策替代 |

禁止使用“差不多完成”“应该能用”“大概通过”等含糊状态。

# 第七部分：资源和训练控制

## 15. 额度与计算资源原则

本项目采用“高级总控审查 + 低级 Agent 执行 + GitHub 事实源”的结构，以减少重复上下文消耗，并保持工程透明。

### 高级模型主要用于

- 科研方案判断；
- 任务拆解；
- GitHub 差异审查；
- 数值和实验可信性判断；
- 失败诊断；
- 论文创新与实验设计。

### 执行模型主要用于

- 安装环境；
- 修改代码；
- 运行测试；
- 执行短实验；
- 收集日志；
- 提交 GitHub。

### 长训练控制

任何超过普通冒烟测试成本的训练，必须满足：

1. 前置阶段通过；
2. 环境和奖励通过审计；
3. 存在短训练可学习证据；
4. 配置、种子和日志已经自动保存；
5. 项目负责人明确批准。

不得用增加训练步数掩盖代码错误、奖励漏洞或算法设计问题。
